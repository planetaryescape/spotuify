The patch's preserve shutdown calls `session.shutdown()` *before* dropping the Spirc handle, so the capture branch is guaranteed rather than the channel-closed wake-up — the ordering comment in `embedded/mod.rs:1103–1107` is correct.
- `Spirc::shutdown` genuinely resets context (`handle_command` → `handle_pause` + `handle_disconnect`, spirc.rs:768–795), and the patch correctly skips it when `preserve` — avoiding the `None`/cleared-state return.
- `SavedPlaybackState` (connect/src/model.rs:172–176) has no derives and `pub(super)` fields; `with_saved_state` takes it by value. The accepted residual limitation is real: on constructor error the saved state is consumed and cannot be cloned/returned.

The restored path's `player.load(uri, false, pos)` (mod.rs:776–780) and `resume_after_reconnect`'s `player.load(native_uri, true, pos)` (mod.rs:1081) therefore preserve the restored queue. The post-restore load's fresh request id passes the filter.

## Findings (non-blocking)

**F1 — Transient registration failure permanently loses the retained queue.** If `with_saved_state` fails for a transient reason (network/auth), `saved` is consumed and `recovery_required` stays set, so every later `ensure_spirc` fails with "restart spotuify before replacing playback" (mod.rs:664–672) until a full non-preserve `shutdown` or daemon restart. The health loop will retry and always fail closed. This is the brief's accepted residual API limitation; I note it is user-visible queue loss on a *transient* error, not just a constructor-edge case.

**F2 — Narrow pre-existing handoff race, with one small delta.** If a foreign handoff lands during the reconnect's registration window, the native steal-guard demotes (clears queue, goes inactive), but the daemon guard's clock check can still pass while stale (`still_wanted`, state.rs:777–789). `resume_after_reconnect` then re-activates via `ensure_active` and calls `Player::load` directly, which bypasses Spirc's "ignored while Not Active" gate. Baseline had the same actor-level reclaim (`play_uri` → `ensure_active`, per the diff's `-` lines at state.rs:4909) but its load went through `spirc.load` and could be dropped in the instant before the Deactivated event clears the activation latch; the direct `Player::load` produces local audio in that micro-window instead. Same end state as the acknowledged R3issue002 (device re-claimed), no queue-ordering contradiction (the demote intentionally clears the queue on handoff in both designs), so I agree with the brief's "no introduced guard weakening" classification — but the direct-load bypass is a real, previously-absent audio-start path inside that race.

**F3 — Seek-back on resume.** When the clock URI matches the native current track, `resume_after_reconnect` uses the daemon clock position (poll-lagged by up to the poll interval) instead of the native position (mod.rs:1064–1071). Baseline resumed at the clock position too; not introduced. Position tracking itself stays fresh within ~5s (fork emits `PositionChanged` every 5s per `player_config`, mod.rs:1215).

**F4 — Transient paused state on reconnect-while-playing.** The restored load (`play=false`) emits `Paused`, which the SpircTask accepts, briefly flipping the restored Playing status to Paused and notifying the cluster before `Spirc::play` re-plays. Cosmetic.

**F5 — Test coverage.** The new daemon test exercises the idle-start payload and snapshot via the mock backend but does not exercise native EOS or the capture/reconnect path — as the brief acknowledges. I did not run cargo; the live journey/native build gates remain root-owned and pending, and I did not treat them as source evidence either way.
