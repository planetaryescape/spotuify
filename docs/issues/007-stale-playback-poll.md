Status: application candidate `7f64f073e9479d7968b3c5a9ed4849e72a775ea8` (tree `fe6a80e1ae37f5f154370932ce5612e30a13a860`) is based on fresh `origin/main` `be192fb6492c4cb9531ddbc07bcf089dab35781a`. During installed queue verification, the native player advanced from one track to the next at 18:02:00.423 UTC. A Web API refresh applied a snapshot of the previous track at 18:02:00.445. CLI status showed the previous track until a later poll at 18:02:23.040. The same queue continued playing, and the follow-up capture verified natural progression from the second track to the third. [Curated installed evidence](../build-log/recovery/evidence/playlist-queue-installed111.json) retains both the timed-out immediate-status assertion and the successful continuation.

It reached B and C on natural track ends while six playback-sync reads overlapped the transitions. Across 94 status samples there were no reversions; C advanced from 14,353 to 64,229 ms over 60 seconds with fresh PCM. Playback was paused afterward. [Curated candidate evidence](../build-log/recovery/evidence/playback-status-candidate.json). The first attempt reconnected before native A-start and failed startup; it does not establish behavior during pending initial activation.

Baseline `v0.1.110` commit `6c90d79c0d9c9c6a2596d62f193595c5a8c49b73` and release `v0.1.111` commit `d3550b81d5b61eda97f00bf1bcf9cc4304e2eebe` share this path. `PlaybackGet` returns the clock snapshot and starts a background refresh (`crates/spotuify-daemon/src/handlers/playback.rs#L95-L106`). Before the fix, a refresh captured only `mutation_seq`; a native track change could leave that sequence unchanged while an older Web API poll was in flight. The focused red test reproduced the stale URI in both the clock and durable playback cache: it expected the new track but found the old one in both places. The [red summary](../build-log/recovery/2026-10-26-playback-poll-freshness.md#the-stale-poll-reached-both-clock-and-cache) records the test command and result.

An earlier candidate `84f34da78df4b73fd7d21c874f9923fd6a534ddc` exposed a second race: native event A could wait for the transport lane while same-provider command B committed, then A replaced B in both clock and cache. Application candidate `7f64f073e9479d7968b3c5a9ed4849e72a775ea8` fixes that ordering. The relay now applies native playback and device-activity state synchronously before awaiting session tracking or metadata; `PlaybackClock::apply_player_event_with_activity` updates them under the clock write lock (`crates/spotuify-daemon/src/clock.rs#L222-L233`). A separate coalescing worker persists the latest clock snapshot after rechecking provider ownership (`crates/spotuify-daemon/src/state.rs#L5482-L5514`, `#L5561-L5580`, `#L5650-L5652`; `crates/spotuify-daemon/src/native_playback_cache.rs#L12-L65`). The event relay does not wait for native-cache I/O.

Poll reads still capture transport mutation and player-transition revisions before on-demand and scheduled requests (`crates/spotuify-sync/src/lib.rs#L72-L75`, `crates/spotuify-daemon/src/handler.rs#L4240-L4276`). Native semantic transitions advance the generation (`crates/spotuify-daemon/src/clock.rs#L222-L233`). Poll commits serialize with transport changes and check the revision and provider ownership around persistence (`crates/spotuify-daemon/src/state.rs#L6048-L6111`). For the active embedded device, a different-URI poll is rejected when Spotify's state-change timestamp predates the local transition. Spotify documents `timestamp` as when playback state last changed ([Get Playback State](https://developer.spotify.com/documentation/web-api/reference/get-information-about-the-users-current-playback)). Foreign-device state remains reconcilable; candidate tests cover an older-timestamp phone snapshot and a newer current-device snapshot.

The store query now breaks equal `fetched_at_ms` ties by descending row ID (`crates/spotuify-store/src/lib.rs#L769-L781`), with a regression test for the newest insert. Persistence errors are logged while the live clock remains authoritative; SQLite durability is not guaranteed when the write fails.

Independent maximum-effort review of application commit `7f64f073e9479d7968b3c5a9ed4849e72a775ea8` passed with no blockers. Accepted limits remain: native-cache I/O or cancellation can leave the durable row behind the live clock; the timestamp guard needs comparable timestamps and rejects only a strictly older value, so missing timestamps, ties, and clock skew do not establish ordering. The review's visualization observation is unchanged from the base commit and is outside this issue.
